# Wasmline Service

Wasmline's first Component contract is the fixed `wasmline:service@1.0.0` world. WIT
defines the Component boundary and Canonical ABI; the `payload: list<u8>` field
still carries the selected Wasmline serialization bytes.

```wit
package wasmline:service@1.0.0;

world plugin {
  import host: interface {
    record request { action: string, codec: string, payload: list<u8> }
    record service-error { code: string, message: string, details: list<u8> }
    invoke: func(request: request) -> result<list<u8>, service-error>
  }

  export plugin: interface {
    record request { action: string, codec: string, payload: list<u8> }
    record service-error { code: string, message: string, details: list<u8> }
    invoke: func(request: request) -> result<list<u8>, service-error>
  }
}
```

## Build Pipeline

For the Kotlin/Wasm WASI sample, the build order is:

1. `wit-bindgen kotlin` generates guest bindings under `build/generated`.
2. Kotlin/Wasm WASI compiles the guest to Core Wasm.
3. `wasm-tools component embed` embeds the WIT world.
4. `wasm-tools component new --adapt wasi_snapshot_preview1=...` creates the raw Component.
5. `wasm-tools validate` and `wasm-tools component wit` verify the result.
6. The AOT catalog resolves backend-specific profiles and digest-locked compiler assets, then compiles the raw Component into the configured `.cwasm` and `.pwasm` targets.
7. The manifest records the `COMPONENT_MODEL + WASMLINE_SERVICE` runtime contract, backend-specific AOT compatibility profiles, and content-addressed target variants with their digests and sizes.

The Gradle entry point is `wasmlineAssembleDebug` or
`wasmlineAssembleRelease`. The CLI exposes individual raw Component stages
through `wit generate`, `componentize`, `component validate`, and
`component inspect`; `compile --execution-model COMPONENT_MODEL` also runs the
Component AOT stage. See the [Gradle Plugin reference](/en/docs/gradle-plugin)
for the complete task graph. The native loader receives only precompiled
Component artifacts and does not run generators or compilers while loading.

Rust can target `wasm32-wasip2` and produce a Component directly. The
`wasmline-samples/rust/sample-component-plugin` fixture pins the forked
`wit-bindgen` 0.57.1 Git tag and does not commit generated bindings.

C and C++ target `wasm32-wasip1` through WASI SDK 33 (the verified baseline). Their fixtures live under
`wasmline-samples/c/sample-component-plugin` and
`wasmline-samples/cpp/sample-component-plugin`. Both consume the canonical WIT
world from `wasmline-plugin-core`, generate bindings under the CMake build
directory, link the generated Component type object, and run
`wasm-tools component new`. A Preview 1 reactor adapter can be supplied when
the selected WASI SDK leaves Preview 1 imports in the Core Wasm.

## Language Bindings

Each guest implements the generated export and uses the generated import. None
of these flows patches Wasmtime, `wit-bindgen`, or the canonical WIT source.

| Language | Binding generation | Plugin export implementation | Host callback API |
|---|---|---|---|
| Kotlin | `wit-bindgen kotlin --world plugin` | `PluginImpl.invoke` | `Host.Import.invoke` |
| Rust | `wit_bindgen::generate!({ world: "plugin" })` | `exports::plugin::Guest::invoke` | `host::invoke` |
| C | `wit-bindgen c --world plugin` | `plugin_invoke` | `host_invoke` |
| C++ | `wit-bindgen cpp --world plugin` | `exports::wasmline::service::Invoke` | `wasmline::service::Invoke` |

Generated source and Component type objects remain build outputs. The C and
C++ fixtures enforce `wit-bindgen 0.57.1` and `wasm-tools 1.256.0` at CMake
configure time; their READMEs contain the complete WASI SDK commands.
The pinned C++ generator emits one `std::expected::value()` use with a
move-only WIT error type. Its fixture applies a fail-closed generated-source
compatibility step that switches that checked access to `operator*` after
`has_value()`; it does not modify `wit-bindgen` source or commit generated code.

The repository validates the native Component Service runtime with a generated
AOT fixture. It does not accept a hand-supplied artifact through an environment
variable:

```shell
./scripts/wasmline jni build --engine cranelift
cd wasmline-multiplatform
rustup target add wasm32-wasip2
./gradlew :wasmline:nativeAotJvmTest \
  -Pwasmline.native.fixtures.targets=x86_64-linux,pulley64 \
  --no-daemon
```

The generated fixture tests callback bytes, an unbound handler, same-session
reentry, and callback into a second Component session. The same JVM task also
loads a Core `RAW_EXPORT` `pulley64` PWASM fixture through the Cranelift native
library. Production Components
are compiled and packaged through the Wasmline Gradle or CLI build tasks, which
select the required `.cwasm` or `.pwasm` artifacts from the configured AOT
compatibility catalog.

## Codec Profiles

The WIT envelope does not make arbitrary business bytes universally decodable.
The `codec` string is part of the request and is checked by the host runtime.

| Profile | Codec ID | Payload rule | Reference |
|---|---|---|---|
| Kotlin envelope | `protobuf` | Kotlin Serialization Protobuf bytes; the Kotlin sample decodes `sample.echo` | `sample-component-plugin` |
| Rust envelope fixture | `protobuf` | Payload is opaque and is echoed or forwarded to `host.invoke`; no Rust business decoder is claimed | `wasmline-samples/rust/sample-component-plugin` |
| C envelope fixture | `protobuf` | Payload is opaque and is copied or forwarded through generated C bindings | `wasmline-samples/c/sample-component-plugin` |
| C++ envelope fixture | `protobuf` | Payload is opaque and is moved or forwarded through generated C++ bindings | `wasmline-samples/cpp/sample-component-plugin` |
| Native typed WIT | not an envelope profile | Business arguments are WIT values and must be described by the Component contract | Explicit typed Component descriptor |

Cross-language plugins that need to exchange business objects must use a codec
implemented by every participant, or expose those objects as typed WIT values.
Matching only the `protobuf` label is not enough.

## Host Callback Adaptation

The generated guest binding calls the WIT import `host.invoke`. Wasmline's
Component session registers that import and maps its `action`, `codec`, and
`payload` fields to the existing `HostDispatcher`. The dispatcher response is
converted back to `result<list<u8>, service-error>` by the runtime.

Therefore a Rust, C, C++, or Kotlin Component plugin implements the WIT world,
not these Core Wasm-only imports:

- `bridge_inbound_copy_params`
- `bridge_inbound_set_response`
- `bridge_outbound_call_host`
- `bridge_outbound_get_response`

The plugin still needs the generated language binding and a WIT `host.invoke`
call. That binding is the portable Component contract; the Wasmline host owns
the adapter into its dispatcher. The Kotlin, Rust, C, and C++ fixtures all
exercise `sample.callback` through their generated host import and propagate
the WIT success or `service-error` back through the plugin export.

The native Wasmtime backend supports this Component path. Browser targets still
advertise only the Core Wasmline bridge and reject Component descriptors during
loading.
