# 组件服务协议

组件服务协议使用固定的 `wasmline:service@1.0.0` world。
WIT 定义 Component 边界和 Canonical ABI；`payload: list<u8>` 只承载业务序列化
字节，WIT 不会解码这些字节。

```wit
package wasmline:service@1.0.0;

world plugin {
  import host: interface {
    record request { action: string, codec: string, payload: list<u8> }
    record service-error { code: string, message: string, details: list<u8> }
    invoke: func(request: request) -> result<list<u8>, service-error>
  }

  export plugin: interface {
    record request { action: string, codec: string, payload: list<u8> }
    record service-error { code: string, message: string, details: list<u8> }
    invoke: func(request: request) -> result<list<u8>, service-error>
  }
}
```

## 构建步骤

Kotlin/Wasm WASI sample 按以下顺序执行：

1. `wit-bindgen kotlin` 在 `build/generated` 下生成 guest binding。
2. Kotlin/Wasm WASI 将 guest 编译成 Core Wasm。
3. `wasm-tools component embed` 嵌入 WIT world。
4. `wasm-tools component new --adapt wasi_snapshot_preview1=...` 生成 raw Component。
5. `wasm-tools validate` 与 `wasm-tools component wit` 校验产物。
6. AOT catalog 选择 backend profile 和已锁定的 compiler 文件，再为配置的 target
   编译 raw Component，生成 `.cwasm` 和 `.pwasm`。
7. manifest 记录 `COMPONENT_MODEL + WASMLINE_SERVICE` contract、每个 AOT profile，
   以及包含 digest 和大小的 target variant。

Gradle 入口是 `wasmlineAssembleDebug` 或 `wasmlineAssembleRelease`。CLI 通过
`wit generate`、`componentize`、`component validate` 和 `component inspect`
提供各个步骤；`compile --execution-model COMPONENT_MODEL` 还会执行 Component
AOT。任务名称参见 [Gradle 插件参考](/zh/docs/gradle-plugin)。Native loader
只接收完成的 Component 产物，加载时不运行生成器或编译器。

Rust 可以使用 `wasm32-wasip2` 直接生成 Component。fixture 位于
`wasmline-samples/rust/sample-component-plugin`，固定 fork 的 `wit-bindgen`
0.57.1 Git tag。生成的 binding 只属于构建输出，不提交到仓库。

C 和 C++ 通过已验证的 WASI SDK 33 编译到 `wasm32-wasip1`。对应 fixture 位于
`wasmline-samples/c/sample-component-plugin` 和
`wasmline-samples/cpp/sample-component-plugin`。它们读取
`wasmline-plugin-core` 内的 canonical WIT world，在 CMake build 目录生成
binding，链接 Component type object，再执行 `wasm-tools component new`。
如果所选 SDK 在 Core Wasm 中保留 Preview 1 import，可以传入 Preview 1 reactor
adapter。

## 多语言 Binding

每种 guest 都实现生成的 export，并调用生成的 import。该步骤不修改 Wasmtime、
`wit-bindgen` 或 canonical WIT 源码。

| 语言 | Binding 生成方式 | 插件 export 实现 | 宿主回调 API |
|---|---|---|---|
| Kotlin | `wit-bindgen kotlin --world plugin` | `PluginImpl.invoke` | `Host.Import.invoke` |
| Rust | `wit_bindgen::generate!({ world: "plugin" })` | `exports::plugin::Guest::invoke` | `host::invoke` |
| C | `wit-bindgen c --world plugin` | `plugin_invoke` | `host_invoke` |
| C++ | `wit-bindgen cpp --world plugin` | `exports::wasmline::service::Invoke` | `wasmline::service::Invoke` |

生成源码和 Component type object 都只属于 build 输出。CMake configure 阶段严格检查 `wit-bindgen 0.57.1` 和 `wasm-tools 1.256.0`，所需的 WASI SDK 命令见各自 README。
C++ 0.57.1 generator 会对 move-only WIT error 生成一次
`std::expected::value()` 调用。fixture 使用 fail-closed 的生成源码兼容步骤，在
`has_value()` 之后将它切换为 `operator*`；该流程不修改 `wit-bindgen` 源码，也不
提交生成代码。

仓库使用生成的 AOT fixture 验证 native Component Service runtime。测试从 fixture
构建任务取得 index，不通过环境变量接收手工提供的产物：

```shell
./scripts/wasmline jni build --engine cranelift
cd wasmline-multiplatform
rustup target add wasm32-wasip2
./gradlew :wasmline:nativeAotJvmTest \
  -Pwasmline.native.fixtures.targets=x86_64-linux,pulley64 \
  --no-daemon
```

fixture 测试 callback bytes、未绑定 handler、同 session 重入，以及 callback 中调用
第二个 Component session。同一个 JVM 任务还会通过 Cranelift native library 加载
一个 Core `RAW_EXPORT` 的 `pulley64` PWASM fixture。生产 Component 由 Wasmline
Gradle 或 CLI 任务编译和打包，并从配置的 AOT catalog 选择 `.cwasm` 或 `.pwasm`。

## Codec Profile

WIT 请求格式不会让任意业务字节自动具备解码能力。`codec` 字符串属于 request
的一部分，并由宿主 runtime 检查。

| Profile | Codec ID | Payload 规则 | 参考实现 |
|---|---|---|---|
| Kotlin 请求字节 | `protobuf` | Kotlin Serialization Protobuf 字节；Kotlin sample 会解码 `sample.echo` | `sample-component-plugin` |
| Rust 请求 fixture | `protobuf` | payload 视为 opaque bytes，只 echo 或转发给 `host.invoke`；不宣称有 Rust 业务解码器 | `wasmline-samples/rust/sample-component-plugin` |
| C 请求 fixture | `protobuf` | payload 视为 opaque bytes，通过生成的 C binding 复制或转发 | `wasmline-samples/c/sample-component-plugin` |
| C++ 请求 fixture | `protobuf` | payload 视为 opaque bytes，通过生成的 C++ binding 移动或转发 | `wasmline-samples/cpp/sample-component-plugin` |
| 原生 typed WIT | 不使用字节 profile | 业务参数直接是 WIT value，必须由 Component 契约描述 | 显式 typed Component descriptor |

跨语言插件如果要交换业务对象，所有参与方必须实现同一个 codec，或将业务对象
设计成 typed WIT。仅把 `codec` 写成 `protobuf` 并不能保证字节可以互相解码。

## 宿主回调适配

生成的 guest binding 调用 WIT import `host.invoke`。Wasmline 的 Component
session 注册这个 import，将 `action`、`codec`、`payload` 映射到
`HostDispatcher`，再把返回值转换成 `result<list<u8>, service-error>`。

因此 Rust、C、C++ 或 Kotlin Component 插件实现的是 WIT world，不需要实现
下面这些仅属于 Core Wasm 路径的 import：

- `bridge_inbound_copy_params`
- `bridge_inbound_set_response`
- `bridge_outbound_call_host`
- `bridge_outbound_get_response`

插件仍然需要使用生成的语言 binding 调用 WIT `host.invoke`。Wasmline 宿主会将该
调用连接到自己的 dispatcher。Kotlin、Rust、C 和 C++ fixture 都通过生成的 host
import 执行 `sample.callback`，并把 WIT success 或 `service-error` 返回给插件 export。

原生 Wasmtime backend 支持这条 Component 路径。浏览器 target 当前仍只声明
支持 Core Wasmline bridge，并会在加载阶段拒绝 Component descriptor。
