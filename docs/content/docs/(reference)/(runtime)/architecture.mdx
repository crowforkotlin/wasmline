## Execution Stacks

Wasmline exposes the same public API from `commonMain` and `hostMain`, then
selects a backend for each target. Android, iOS, macOS, Linux, and Windows use
`wasmline-core` (C/C++, built with Zig 0.16.0) and the Wasmtime C API. Kotlin/JS
and Kotlin/WasmJS use the browser WebAssembly API; Wasmtime is not loaded.

### Native Target Stack — Android · iOS · macOS · Linux · Windows

```text
Host Application  (commonMain / hostMain)
        │
        │  module.link<T>()      — IR-synthesized typed outbound proxy
        │  module.bind(impl)     — IR-synthesized inbound dispatch registration
        │
        ▼
Platform actual  (jniMain / nativeMain)
        │  JNI external declarations          — JVM / Android
        │  Kotlin/Native C Interop (.def)     — iOS, macOS, Linux, Windows
        ▼
wasmline-core  (C/C++ · Zig 0.16.0)
        │  Engine.cpp              — engine creation and backend selection
        │  Module.cpp/Component.cpp — AOT deserialization and caches
        │  Session variants        — service, Raw Export, and Component calls
        │  Api.cpp                 — JNI / C Interop calls (load, invoke, setOutbound, release)
        ▼
wasmtime C-API  v48.0.1
        │  Sandboxed execution; hardware-accelerated AOT; per-session memory isolation
        ▼
Precompiled artifact  (.cwasm — Cranelift native AOT  |  .pwasm — Pulley bytecode; Core or Component is declared separately)
```

The engine and artifact types are selected separately. A Cranelift runtime loads
CWASM only when the profile and complete target identity match. It can use PWASM
only when no matching CWASM exists and the runtime reports a matching Pulley
profile. A Pulley runtime accepts PWASM. iOS uses `pulley64` PWASM.

### Web Target Stack — Kotlin/JS · Kotlin/WasmJS

```text
Host Application  (commonMain / hostMain)
        │
        │  module.link<T>()      — IR-generated proxy
        │  module.bind(impl)     — IR-generated dispatch registration
        │
        ▼
webMain / jsMain / wasmJsMain
        │  WasmlineWeb · WebWasmArtifacts · WebWasmPlugin
        ▼
Inline JS runtime  (Kotlin js() interop — no external .js files emitted)
        │
        ▼
Browser WebAssembly API  (WebAssembly.Module + WebAssembly.Instance)
        │
        ├── Import namespace: wasi_snapshot_preview1
        │     fd_write         — UTF-8 stdout/stderr routed through WasmlineLog or println
        │     random_get       — Kotlin Random.nextBytes
        │     clock_time_get   — Date.now() converted from milliseconds to nanoseconds
        │
        └── Import namespace: env  (Wasmline bridge protocol)
              bridge_inbound_copy_params     — write action + payload into Wasm linear memory
              bridge_inbound_set_response    — extract response bytes from Wasm linear memory
              bridge_outbound_call_host      — synchronous plugin-to-host dispatch callback
              bridge_outbound_get_response   — copy oversized outbound response to caller buffer
        │
        ▼
Plugin binary  (raw .wasm — asynchronously prefetched with Fetch, then loaded from the byte cache)
```

## Manifest and Artifact Selection

One signed manifest describes the plugin contract and all available artifacts:

```text
SignedManifest
└── exact signed payload bytes
    └── WasmlineManifest
        ├── runtimeContract
        ├── aotCompatibilityProfiles
        └── artifactTargets
            └── variants (profile IDs, SHA-256, size)
```

The manifest format and signature algorithm are fixed. The loader checks the
format version, resolves a trusted key, verifies Ed25519 over the original
payload bytes, and then decodes and validates the manifest. Artifact paths use
the digest and extension:

```text
artifacts/sha256/{digest-prefix}/{digest}.{extension}
```

The native engine reports supported formats, backend AOT profile IDs, Wasmline
release, bridge ABI, operating system, architecture, pointer width, and CPU
features. The loader builds one profile-ID map and scans the manifest entries
once. It does not scan package directories.

For a remote load, the loader requests `manifest.wlm`, selects one variant, and
streams that artifact while checking its declared size and SHA-256. It does not
download the offline ZIP. A Core Web `.wasm` variant is independent of native
profiles and is stored once. Raw Component Wasm remains a build input.

## Execution Models

The runtime selects the backend from `WasmlineArtifactDescriptor`. A file
extension does not select the execution model.

| Execution model   | Invocation protocol | Runtime boundary                                                                    | Core response frame |
| ----------------- | ------------------- | ----------------------------------------------------------------------------------- | ------------------- |
| `CORE_WASM`       | `WASMLINE_SERVICE`  | `Session`, action router, and linear memory                                         | Yes                 |
| `CORE_WASM`       | `RAW_EXPORT`        | `CoreWasmModule`/`CoreWasmSession`, exports, synchronous imports, and linear memory | No                  |
| `COMPONENT_MODEL` | `WASMLINE_SERVICE`  | `ComponentSession` and the fixed `wasmline.wit` request format                      | No                  |
| `COMPONENT_MODEL` | `COMPONENT_EXPORT`  | `ComponentSession` and Component Model values                                       | No                  |

`WASMLINE_SERVICE` selects the Wasmline service API. With `CORE_WASM`, response
bytes use the fixed `WLMF` marker and one-byte `frameVersion` (`1`). With
`COMPONENT_MODEL`, requests use the fixed `wasmline:service@1.0.0` WIT format and
Canonical ABI. The execution model determines which representation is used.

Raw Export calls use an explicitly declared numeric ABI. The current public raw value set is `i32`, `i64`, `f32`, and `f64`. Export signatures, synchronous imports, memory, and required features are stored in the signed `runtimeContract.rawAbi` model rather than encoded in free-form metadata. Raw calls do not allocate or parse a Core response frame.

Component Model calls deserialize a precompiled Component `.cwasm` or `.pwasm`
through the Wasmtime Component Model API. They use typed Component values and do
not require Core linear memory, `__wasmline_wasi_entry`, or the Core response
frame. The loader does not run `wit-bindgen`, `wasm-tools`, or `wasmtime compile`;
the Gradle and CLI build tasks do that before loading. `contractMetadata` can
record call information for validation and documentation, but is not compiler
input.

All four combinations return the same success or failure shape. A missing
service action binding returns `ACTION_NOT_BOUND`; it is not an empty successful
payload. Core Service reports the failure in its response frame, while Raw
Export and Component Model return a typed failure. Exceptions are reserved for
invalid calls, unrecoverable runtime state, and failures that prevent a result
from being created.

The Web implementation supports both `CORE_WASM + WASMLINE_SERVICE` and
`CORE_WASM + RAW_EXPORT` through the browser `WebAssembly.Module` and
`WebAssembly.Instance` APIs. Raw sessions use direct numeric exports, imports
registered before instantiation, and checked linear-memory access; they do not
use the Service response frame. Component Model typed calls remain native-only.
Web and native share the Core ABI contract while retaining different backends:
Web uses JS/WasmJS bindings and raw `.wasm`, while native uses the Wasmtime
bridge and `.cwasm`/`.pwasm` AOT artifacts.

## Module Dependency Graph

```text
wasmline-cli ───────────► wasmline-plugin-core ───────► wasmline-loader ──► wasmline
wasmline-gradle-plugin ─► wasmline-plugin-core
        │
        └───────────────► wasmline-kotlin-plugin  (compile-time IR transformation)

wasmline ◄──── native runtime assets ──── wasmline-engine-cranelift / wasmline-engine-pulley
wasmline-network-ktor / wasmline-network-okhttp ──────► wasmline-loader
wasmline-core (C/C++) ◄──── JNI / Native C Interop ─── wasmline
wasmline-bom ── strict same-version constraints ──────► published Wasmline modules
```

Network, cache, trusted-key, and load-request APIs belong to `wasmline-loader`.
Ktor and OkHttp implement its suspend network SPI; the core runtime has no HTTP
dependency. A host needs one of them only for a remote cache miss. Ktor covers
JVM, Android, Apple, Linux, and Windows Native; OkHttp covers JVM and Android.
Browser raw `.wasm` loading uses `WasmlineWeb.prefetch()`.

## Repository Structure

```text
wasmline/
├── wasmline-core/                      # C/C++ wasmtime bridge (Engine, Module, Session, Api)
├── wasmline-multiplatform/
│   ├── wasmline/                       # Core Kotlin runtime — execution, dispatch, serialization SPI
│   │   ├── commonMain/                 # Platform-agnostic contracts and bridge abstractions
│   │   ├── hostMain/                   # Host API: Wasmline, WasmlineLoadState, link<T>(), bind()
│   │   ├── jniMain/                    # JVM / Android actual — JNI external declarations
│   │   ├── nativeMain/                 # Kotlin/Native actuals and C Interop
│   │   ├── webMain/                    # Shared Web host runtime and expect binding contract
│   │   ├── jsMain/                     # Kotlin/JS binding actuals
│   │   ├── wasmJsMain/                 # Kotlin/WasmJS binding actuals
│   │   └── wasmWasiMain/               # Core and Component Service guest hooks
│   ├── wasmline-loader/                # Load requests/options, cache/network SPI, .wlm verification
│   ├── wasmline-plugin-core/           # Shared Core/Component build, signing, packaging, and toolchain logic
│   ├── wasmline-cli/                   # CLI adapters for plugin-core and loader operations
│   ├── wasmline-android/               # Android native bindings (CMake / JNI C++)
│   ├── wasmline-kotlin-plugin/         # Kotlin IR compiler plugin — bridge synthesis, call-site rewriting
│   ├── wasmline-gradle-plugin/         # Consumer DSL and tasks built on compiler plugin and plugin-core
│   ├── wasmline-engine-cranelift/      # Cranelift runtime distribution and platform variants
│   ├── wasmline-engine-pulley/         # Pulley runtime distribution and platform variants
│   ├── wasmline-network-ktor/          # Ktor loader network adapter
│   ├── wasmline-network-okhttp/        # OkHttp loader network adapter
│   ├── wasmline-bom/                   # Strict same-version Maven platform constraints
│   ├── wasmline-plugin-test/           # End-to-end plugin and native integration tests
│   └── wasmline-build-logic/           # Shared Gradle convention plugins
├── wasmline-samples/
│   ├── kotlin/                         # Kotlin plugins, Component fixtures, and host applications
│   ├── rust/                           # Rust Component fixtures
│   ├── c/                              # C Component fixture
│   └── cpp/                            # C++ Component fixture
├── scripts/                            # Environment, assets, lint, and version synchronization
├── build/                              # Root build outputs, including build/platforms/ wasmtime min C-API assets
└── docs/                               # Documentation site (Next.js + Fumadocs)
```
