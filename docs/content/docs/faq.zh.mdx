# 常见问题

<details>
<summary><strong>浏览器执行路径如何在没有 wasmtime 的情况下实例化插件？</strong></summary>

Web 目标实现（`webMain` / `jsMain` / `wasmJsMain`）通过浏览器原生 WebAssembly 运行时，直接调用 `WebAssembly.Module` 和 `WebAssembly.Instance`。运行时层通过 Kotlin `js()` interop 内嵌为 JavaScript 代码——编译过程中不会生成外部 JS 文件。

该运行时层提供：

- **`wasi_snapshot_preview1` shim**：`fd_write`（stdout/stderr 映射到 `console.log`/`console.error`）、`random_get`（`crypto.getRandomValues`）、`clock_time_get`（以纳秒精度使用 `Date.now()`）
- **Wasmline bridge 协议**（`env` 命名空间）：`bridge_inbound_copy_params`、`bridge_inbound_set_response`、`bridge_outbound_call_host`、`bridge_outbound_get_response`

payload 数据以 Base64 编码字符串跨越 Kotlin–JS 线性内存边界（`BrowserPayloadEncoding`）。AOT 编译产物（`.cwasm`、`.pwasm`）不被接受。

</details>

<details>
<summary><strong><code>.cwasm</code> 与 <code>.pwasm</code> 产物有什么区别——为什么不用原始 <code>.wasm</code>？</strong></summary>

这三种产物类型在 Wasmline 流水线中相关，但它们在**编译发生的时机**以及**编译目标**上有根本区别：

| 产物 | 编译时机 | 执行方式 | 版本关联性 |
|---|---|---|---|
| `.wasm` | 源格式；仅由浏览器路径直接加载 | 浏览器 WebAssembly 运行时 | **无 — 不与 Wasmtime 版本绑定** |
| `.cwasm` | 由 `wasmtime compile` 通过 Cranelift 提前编译 | 直接在原生硬件上执行（例如 arm64 machine code） | 与编译它的 wasmtime 版本关联 |
| `.pwasm` | 由 `wasmtime compile` 通过 Cranelift 提前编译 | wasmtime **Pulley** 解释器 | 与编译它的 wasmtime 版本关联 |

**`.cwasm`（平台特定 AOT）** 会为特定 target triple（例如 `aarch64-android`）生成原生机器码。吞吐量最高；但每个平台都需要单独产物。

**`.pwasm`（Pulley AOT）** 与 `.cwasm` 一样，都是通过相同的 Cranelift 流水线编译而来，但其目标不是原生机器码，而是 wasmtime 的 **Pulley** 字节码 ISA，运行时再由 Pulley 解释器执行。关键在于，`.pwasm` **不是**把原始 `.wasm` 文件交给解释器运行——它是一个完整的、由 Cranelift 预编译得到的产物，与 `.cwasm` 走的是相同编译路径，只是目标后端不同。`pulley64.pwasm` 可在所有 64 位原生 wasmtime 目标上运行；32 位目标使用匹配的 `pulley32.pwasm`。

原始 `.wasm` 只有浏览器路径可以直接接受。Wasmline 原生运行时要求预编译的 `.cwasm` 或 `.pwasm`；这两者都是特定 wasmtime 发行版的输出，因此升级 wasmtime 后会失效，必须重新编译。

Wasmline 原生运行时不会通过 Pulley 引擎加载原始 `.wasm`。必须提前生成 `.pwasm`，让 Pulley 解释器直接执行预编译字节码，避免进程内编译步骤；这对 Android 这类内存受限环境尤其重要。

<Callout type="info" title="版本绑定">
`.cwasm` 与 `.pwasm` 都**与生成它们的 wasmtime 编译器版本绑定**。一旦升级 wasmtime 版本，所有已编译产物都会失效，必须重新编译。正因如此，除 Web 外的所有原生目标都使用预编译的 `.cwasm` 或 `.pwasm`，而不是原始 `.wasm`。Web 是唯一的例外，它依赖浏览器自身的 WebAssembly 运行时并使用原始 `.wasm` 文件。
</Callout>

</details>

<details>
<summary><strong>哪个引擎模块应该加载哪种产物？</strong></summary>

| 引擎模块 | 支持的产物 | 选择策略 |
|---|---|---|
| `wasmline-engine-cranelift` | `.cwasm` 和 `.pwasm` | 优先匹配的 `.cwasm`，缺少时回退到可移植 `.pwasm` |
| `wasmline-engine-pulley` | 仅 `.pwasm` | 通过 Pulley 解释器执行可移植字节码 |
| iOS 运行时 | 仅 `.pwasm` | iOS 只能使用 Pulley 解释器，不能加载原生可执行 AOT |

引擎模块名称与产物格式不是一一对应的：Cranelift 是生成两种 AOT 格式的编译器；Pulley 是 `.pwasm` 使用的字节码 ISA 和解释器。Cranelift Wasmtime 构建同时包含两种能力；仅 Pulley 构建只包含 Pulley 能力。

</details>

<details>
<summary><strong>Core Wasm、Raw Export 和 Component Model 调用有什么区别？</strong></summary>

同一套 action 与字节 payload 服务 API 可以让 `WASMLINE_SERVICE` 与两种执行模型组合：Core 使用既有线性内存桥接，Component Model 使用固定 `wasmline.wit` envelope。明确的数值 export ABI 使用 `CORE_WASM + RAW_EXPORT`；业务专用 typed WIT value 使用 `COMPONENT_MODEL + COMPONENT_EXPORT`。

运行时 Component Model 路径的输入是已经编译完成的 component binary。加载时不会运行 `wit-bindgen` 或生成 adapter；可选的 plugin 构建流水线可以通过 plugin-core、Gradle 和 CLI 在加载前完成 WIT 绑定与 Component 组装。`contractMetadata` 仍然只是描述 export 契约，不是 WIT 编译器的输入。详见 [Wasmline Service 指南](/zh/docs/component-service)。

</details>

<details>
<summary><strong>插件没有绑定 action 时会发生什么？</strong></summary>

调用返回包含 `WasmlineErrorCode.ACTION_NOT_BOUND` 的 `WasmlineCallResult.Failure`。它不返回空的成功 payload，也不会导致宿主崩溃。未知 action、无效 payload、handler 失败、trap 和响应帧格式错误，在运行时能够构造可靠结果时都遵循相同的结果优先规则。

使用 `callResult`、`invokeRawResult` 或 `invokeComponentResult`，并读取 `Failure.error.code`。`getOrNull()` 与 `errorOrNull()` 是无异常辅助方法。`throwOnFailure()` 只为明确选择异常风格的调用方提供适配，不是默认的传输行为。

</details>

<details>
<summary><strong><code>WLMF</code> 与 <code>frameVersion</code> 表示什么？</strong></summary>

`WLMF` 是 Wasmline Core 响应帧的四字节 magic 标记，用于识别响应格式。它不是签名、加密机制或安全校验。完整性和真实性由产物 hash、manifest 与签名机制负责。

`frameVersion` 是一个字节的响应布局版本。当前值为 `1`；它不表示 Wasmtime、Kotlin、框架或业务 API 版本。读取方只接受当前值 `1`。Raw Export 和 Component Model 调用不使用该 Core 响应帧。

</details>

<details>
<summary><strong>Kotlin IR 编译器插件是宿主集成的必需项吗？</strong></summary>

编译器插件并非必需。底层 `Wasmline.call(action, bytes): ByteArray` API 始终可用于手动分发。如果未应用 `wasmline-kotlin-plugin`——通常通过 `wasmline-gradle-plugin` 间接应用——`link<T>()` 与 `bind(impl)` 调用点会在运行时抛出 `UnsupportedOperationException`。

</details>

<details>
<summary><strong>插件执行的隔离模型是什么？</strong></summary>

在原生目标上，每次插件调用都在独立的 `Session` 实例中执行，并维护其自己的 Wasm 线性内存区域。除非宿主通过 wasmtime 的 preopened-directory 或 socket-capability 模型显式授予能力，否则插件无法访问宿主进程内存、宿主文件系统或网络。在 Web 目标上，对等的内存隔离由浏览器原生 WebAssembly 沙箱提供。

</details>
