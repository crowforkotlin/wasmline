# Platform Architecture

## Architecture Mind Map

![Wasmline Architecture Mind Map](/images/wasmline_mind_en.png)

## Execution Stacks

Wasmline exposes a single API from `commonMain` / `hostMain` and selects an execution path per target platform. On native targets (Android, iOS, macOS, Linux, Windows), plugins execute through `wasmline-core` (C/C++, compiled with Zig 0.16.0) into the wasmtime C-API. On Web targets (Kotlin/JS, Kotlin/WasmJS), plugins execute through an inline JS runtime on the browser-native WebAssembly API — wasmtime is not involved.

### Native Target Stack — Android · iOS · macOS · Linux · Windows

```text
Host Application  (commonMain / hostMain)
        │
        │  module.link<T>()      — IR-synthesized typed outbound proxy
        │  module.bind(impl)     — IR-synthesized inbound dispatch registration
        │
        ▼
Platform actual  (jniMain / nativeMain)
        │  JNI external declarations          — JVM / Android
        │  Kotlin/Native C Interop (.def)     — iOS, macOS, Linux, Windows
        ▼
wasmline-core  (C/C++ · Zig 0.16.0)
        │  Engine.cpp              — Wasmtime engine lifecycle and backend selection
        │  Module.cpp/Component.cpp — deserialize-only Core and Component artifact caches
        │  Session variants        — Wasmline Service, Raw Export, and Component calls
        │  Api.cpp                 — JNI / C Interop surface (load, invoke, setOutbound, release)
        ▼
wasmtime C-API  v47.0.2
        │  Sandboxed execution; hardware-accelerated AOT; per-session memory isolation
        ▼
Precompiled artifact  (.cwasm — Cranelift native AOT  |  .pwasm — Pulley bytecode; Core or Component is declared separately)
```

The artifact and engine layers are separate capabilities. The Cranelift Wasmtime build includes both the Cranelift compiler and the Pulley interpreter, so it can load matching `.cwasm` artifacts and fall back to `.pwasm`. The Pulley engine build contains only the Pulley interpreter and accepts `.pwasm` only. iOS uses the Pulley engine and therefore always selects `.pwasm`.

### Web Target Stack — Kotlin/JS · Kotlin/WasmJS

```text
Host Application  (commonMain / hostMain)
        │
        │  module.link<T>()      — IR-synthesized proxy (same IR pipeline as native)
        │  module.bind(impl)     — dispatch registration (same IR pipeline as native)
        │
        ▼
webMain / jsMain / wasmJsMain
        │  WasmlineWeb · WebWasmArtifacts · WebWasmPlugin
        ▼
Inline JS runtime  (Kotlin js() interop — no external .js files emitted)
        │
        ▼
Browser WebAssembly API  (WebAssembly.Module + WebAssembly.Instance)
        │
        ├── Import namespace: wasi_snapshot_preview1
        │     fd_write         — UTF-8 stdout/stderr routed through WasmlineLog or println
        │     random_get       — Kotlin Random.nextBytes
        │     clock_time_get   — Date.now() converted from milliseconds to nanoseconds
        │
        └── Import namespace: env  (Wasmline bridge protocol)
              bridge_inbound_copy_params     — write action + payload into Wasm linear memory
              bridge_inbound_set_response    — extract response bytes from Wasm linear memory
              bridge_outbound_call_host      — synchronous plugin-to-host dispatch callback
              bridge_outbound_get_response   — copy oversized outbound response to caller buffer
        │
        ▼
Plugin binary  (raw .wasm — asynchronously prefetched with Fetch, then loaded from the byte cache)
```

## Execution Models

The runtime selects the backend from `WasmlineArtifactDescriptor`. File extensions do not select the execution model.

| Execution model | Invocation protocol | Runtime boundary | Core response frame |
|---|---|---|---|
| `CORE_WASM` | `WASMLINE_SERVICE` | `Session`, action router, and linear memory | Yes |
| `CORE_WASM` | `RAW_EXPORT` | `RawModuleSession` and declared Core numeric ABI | No |
| `COMPONENT_MODEL` | `WASMLINE_SERVICE` | `ComponentSession` and the fixed `wasmline.wit` envelope | No |
| `COMPONENT_MODEL` | `COMPONENT_EXPORT` | `ComponentSession` and Component Model values | No |

`WASMLINE_SERVICE` selects the Wasmline service API. With `CORE_WASM`, its response bytes use the fixed `WLMF` magic marker and a one-byte `frameVersion` with the current value `1`. With `COMPONENT_MODEL`, it uses the fixed `wasmline:service@1.0.0` WIT envelope and Canonical ABI instead. The execution model therefore selects the transport; the protocol alone does not.

Raw Export calls use an explicitly declared numeric ABI. The current public raw value set is `i32`, `i64`, `f32`, and `f64`. They do not allocate or parse a Core response frame.

Component Model calls deserialize a precompiled Component `.cwasm` or `.pwasm` artifact through the Wasmtime Component Model API. They use Component Model typed values and do not require Core linear memory, `__wasmline_wasi_entry`, or the Core response frame. The runtime loader does not run `wit-bindgen`, `wasm-tools`, or `wasmtime compile`; the optional build pipeline in `wasmline-plugin-core`, the Gradle plugin, and the CLI completes that build work before loading. Optional `contractMetadata` records a call contract for validation and documentation; it is not compiler input.

All three paths expose the same result semantics. A missing action binding returns `ACTION_NOT_BOUND` as a failure result. It is not encoded as an empty successful payload and does not require an exception. The Core path reports this through its response frame; Raw Export and Component Model report it through their typed result carrier. Exceptions remain for invalid programming contracts, unrecoverable runtime state, and failures that prevent construction of a result.

The current browser implementation supports the Core Wasmline bridge only. Raw Export and Component Model typed calls are routed through the native backend because they require the Wasmtime C API. This is a target capability boundary, not a change to the artifact model.

## Module Dependency Graph

```text
wasmline-cli ───────────► wasmline-plugin-core ───────► wasmline-loader ──► wasmline
wasmline-gradle-plugin ─► wasmline-plugin-core
        │
        └───────────────► wasmline-kotlin-plugin  (compile-time IR transformation)

wasmline ◄──── native runtime assets ──── wasmline-engine-cranelift / wasmline-engine-pulley
wasmline-network-ktor / wasmline-network-okhttp ──────► wasmline-loader
wasmline-core (C/C++) ◄──── JNI / Native C Interop ─── wasmline
```

Network, cache, trusted-key, and load-request APIs belong to `wasmline-loader`. The Ktor and OkHttp artifacts implement the loader's suspend network SPI and depend toward the loader; the core `wasmline` runtime has no HTTP-engine dependency. Applications select an adapter only for remote cache misses. Ktor covers JVM, Android, Apple, Linux, and Windows Native through CIO, OkHttp, Darwin, Curl, and WinHTTP engines; OkHttp covers JVM and Android. Browser raw `.wasm` loading remains a separate `WasmlineWeb.prefetch()` flow.

## Repository Structure

```text
wasmline/
├── wasmline-core/                      # C/C++ wasmtime bridge (Engine, Module, Session, Api)
├── wasmline-multiplatform/
│   ├── wasmline/                       # Core Kotlin runtime — execution, dispatch, serialization SPI
│   │   ├── commonMain/                 # Platform-agnostic contracts and bridge abstractions
│   │   ├── hostMain/                   # Host API: Wasmline, WasmlineLoadState, link<T>(), bind()
│   │   ├── jniMain/                    # JVM / Android actual — JNI external declarations
│   │   ├── nativeMain/                 # Kotlin/Native actuals and C Interop
│   │   ├── webMain/                    # Shared Web host runtime and expect binding contract
│   │   ├── jsMain/                     # Kotlin/JS binding actuals
│   │   ├── wasmJsMain/                 # Kotlin/WasmJS binding actuals
│   │   └── wasmWasiMain/               # Core and Component Service guest hooks
│   ├── wasmline-loader/                # Load requests/options, cache/network SPI, .wlm verification
│   ├── wasmline-plugin-core/           # Shared Core/Component build, signing, packaging, and toolchain logic
│   ├── wasmline-cli/                   # CLI adapters for plugin-core and loader operations
│   ├── wasmline-android/               # Android native bindings (CMake / JNI C++)
│   ├── wasmline-kotlin-plugin/         # Kotlin IR compiler plugin — bridge synthesis, call-site rewriting
│   ├── wasmline-gradle-plugin/         # Consumer DSL and tasks built on compiler plugin and plugin-core
│   ├── wasmline-engine-cranelift/      # Cranelift runtime distribution and platform variants
│   ├── wasmline-engine-pulley/         # Pulley runtime distribution and platform variants
│   ├── wasmline-network-ktor/          # Ktor loader network adapter
│   ├── wasmline-network-okhttp/        # OkHttp loader network adapter
│   ├── wasmline-plugin-test/           # End-to-end plugin and native integration tests
│   └── wasmline-build-logic/           # Shared Gradle convention plugins
├── wasmline-samples/
│   ├── kotlin/                         # Kotlin plugins, Component fixtures, and host applications
│   ├── rust/                           # Rust Component fixtures
│   ├── c/                              # C Component fixture
│   └── cpp/                            # C++ Component fixture
├── scripts/                            # Environment, assets, lint, and version synchronization
├── build/                              # Root build outputs, including build/platforms/ wasmtime min C-API assets
└── docs/                               # Documentation site (Next.js + Fumadocs)
```
