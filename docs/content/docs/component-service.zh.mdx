# Wasmline Service

Wasmline 的 Component Service 契约是固定的 `wasmline:service@1.0.0` world。WIT 负责
Component 边界和 Canonical ABI；`payload: list<u8>` 仍然承载选定的 Wasmline
序列化字节，并不会自动把业务对象变成跨语言对象。

```wit
package wasmline:service@1.0.0;

world plugin {
  import host: interface {
    record request { action: string, codec: string, payload: list<u8> }
    record service-error { code: string, message: string, details: list<u8> }
    invoke: func(request: request) -> result<list<u8>, service-error>
  }

  export plugin: interface {
    record request { action: string, codec: string, payload: list<u8> }
    record service-error { code: string, message: string, details: list<u8> }
    invoke: func(request: request) -> result<list<u8>, service-error>
  }
}
```

## 构建流水线

Kotlin/Wasm WASI sample 的顺序是：

1. `wit-bindgen kotlin` 在 `build/generated` 下生成 guest binding。
2. Kotlin/Wasm WASI 将 guest 编译成 Core Wasm。
3. `wasm-tools component embed` 嵌入 WIT world。
4. `wasm-tools component new --adapt wasi_snapshot_preview1=...` 生成 raw Component。
5. `wasm-tools validate` 与 `wasm-tools component wit` 校验产物。
6. AOT catalog 解析区分 backend 的 profile 与摘要锁定的 compiler asset，再将 raw Component 编译为已配置 target 的 `.cwasm` 和 `.pwasm`。
7. manifest 记录 `COMPONENT_MODEL + WASMLINE_SERVICE` runtime contract、区分 backend 的 AOT compatibility profile，以及包含 digest 和大小的内容寻址 target variant。

Gradle 入口是 `wasmlineAssembleDebug` 或 `wasmlineAssembleRelease`。CLI 通过
`wit generate`、`componentize`、`component validate` 和 `component inspect`
提供 raw Component 的各个阶段；`compile --execution-model COMPONENT_MODEL`
还会执行 Component AOT。完整任务图参见 [Gradle 插件参考](/zh/docs/gradle-plugin)。
native loader 只接收预编译 Component 产物，加载时不运行生成器或编译器。

Rust 可以使用 `wasm32-wasip2` 直接生成 Component。Rust fixture 位于
`wasmline-samples/rust/sample-component-plugin`，并固定 fork 的
`wit-bindgen` 0.57.1 Git tag，不提交生成 bindings。

C 和 C++ 通过 WASI SDK 33（已验证基线）编译到 `wasm32-wasip1`。对应 fixture 位于
`wasmline-samples/c/sample-component-plugin` 和
`wasmline-samples/cpp/sample-component-plugin`。两者直接读取
`wasmline-plugin-core` 内的 canonical WIT world，在 CMake build 目录生成
bindings，链接生成的 Component type object，再执行
`wasm-tools component new`。如果所选 WASI SDK 仍在 Core Wasm 中保留
Preview 1 import，可以显式传入 Preview 1 reactor adapter。

## 多语言 Binding

每种 guest 都实现生成的 export，并通过生成的 import 回调宿主。该流程不修改
Wasmtime、`wit-bindgen` 或 canonical WIT 源码。

| 语言 | Binding 生成方式 | 插件 export 实现 | 宿主回调 API |
|---|---|---|---|
| Kotlin | `wit-bindgen kotlin --world plugin` | `PluginImpl.invoke` | `Host.Import.invoke` |
| Rust | `wit_bindgen::generate!({ world: "plugin" })` | `exports::plugin::Guest::invoke` | `host::invoke` |
| C | `wit-bindgen c --world plugin` | `plugin_invoke` | `host_invoke` |
| C++ | `wit-bindgen cpp --world plugin` | `exports::wasmline::service::Invoke` | `wasmline::service::Invoke` |

生成源码和 Component type object 都只属于 build 输出。C 与 C++ fixture 会在
CMake configure 阶段严格检查 `wit-bindgen 0.57.1` 和
`wasm-tools 1.256.0`，完整的 WASI SDK 命令见各自 README。
C++ 0.57.1 generator 会对 move-only WIT error 生成一次
`std::expected::value()` 调用。fixture 使用 fail-closed 的生成源码兼容步骤，在
`has_value()` 之后将它切换为 `operator*`；该流程不修改 `wit-bindgen` 源码，也不
提交生成代码。

先将一个完成的 Rust、C 或 C++ Component 编译为 `.cwasm` 或 `.pwasm`，再把该 AOT 产物交给 native runtime 验证：

```shell
cd wasmline-multiplatform
WASMLINE_LIVE_TESTS=1 \
WASMLINE_TEST_COMPONENT_SERVICE=/absolute/path/to/plugin.pwasm \
./gradlew :wasmline:jvmTest \
  --tests 'crow.wasmline.test.wasmtime.NativeComponentServiceIntegrationTest' \
  --rerun-tasks --console=plain
```

四项测试分别覆盖 callback bytes、未绑定 handler、同 session 重入，以及 callback
中调用第二个 Component session。

## Codec Profile

WIT envelope 不会让任意业务字节自动具备通用解码能力。`codec` 字符串属于
request 的一部分，并由宿主 runtime 检查。

| Profile | Codec ID | Payload 规则 | 参考实现 |
|---|---|---|---|
| Kotlin envelope | `protobuf` | Kotlin Serialization Protobuf 字节；Kotlin sample 会解码 `sample.echo` | `sample-component-plugin` |
| Rust envelope fixture | `protobuf` | payload 视为 opaque bytes，只 echo 或转发给 `host.invoke`；不宣称有 Rust 业务解码器 | `wasmline-samples/rust/sample-component-plugin` |
| C envelope fixture | `protobuf` | payload 视为 opaque bytes，通过生成的 C binding 复制或转发 | `wasmline-samples/c/sample-component-plugin` |
| C++ envelope fixture | `protobuf` | payload 视为 opaque bytes，通过生成的 C++ binding 移动或转发 | `wasmline-samples/cpp/sample-component-plugin` |
| 原生 typed WIT | 不使用 envelope profile | 业务参数直接是 WIT value，必须由 Component 契约描述 | 显式 typed Component descriptor |

跨语言插件如果要交换业务对象，必须让所有参与方实现同一个 codec，或将业务
对象直接设计成 typed WIT。仅仅把 `codec` 都写成 `protobuf` 并不能保证业务
字节可以互相解码。

## 宿主回调适配

生成的 guest binding 调用 WIT import `host.invoke`。Wasmline 的 Component
session 注册这个 import，并把其中的 `action`、`codec`、`payload` 映射到已有的
`HostDispatcher`；宿主返回值再由 runtime 转换成
`result<list<u8>, service-error>`。

因此 Rust、C、C++ 或 Kotlin Component 插件实现的是 WIT world，不需要实现
下面这些仅属于 Core Wasm 路径的 import：

- `bridge_inbound_copy_params`
- `bridge_inbound_set_response`
- `bridge_outbound_call_host`
- `bridge_outbound_get_response`

插件仍然需要使用生成的语言 binding 调用 WIT `host.invoke`。这个 binding 是
可移植的 Component 契约；Wasmline 宿主负责把它接入自己的 dispatcher。
Kotlin、Rust、C 和 C++ fixture 都通过各自生成的 host import 执行
`sample.callback`，并把 WIT success 或 `service-error` 继续传回插件 export。

原生 Wasmtime backend 支持这条 Component 路径。浏览器 target 当前仍只声明
支持 Core Wasmline bridge，并会在加载阶段拒绝 Component descriptor。
