# Frequently Asked Questions

<details>
<summary><strong>Must every application add a Wasmline network module?</strong></summary>

No. Local artifacts and local manifests use `wasmline-loader` without Ktor or OkHttp. Online remote-manifest loading needs one of `wasmline-network-ktor`, `wasmline-network-okhttp`, a custom `WasmlineNetworkClient`, or a custom remote resolver. The built-in resolver checks its cache first, so it can also load a remote package without a network client when both the manifest is fresh and the selected artifact is cached.

The adapters depend on `wasmline-loader`; neither adapter is hardcoded into the core `wasmline` runtime. Ktor publishes JVM, Android, Apple, Linux, and Windows Native variants. OkHttp publishes JVM and Android variants. The browser uses `WasmlineWeb.prefetch()` for raw `.wasm` instead.

</details>

<details>
<summary><strong>How does the browser execution path instantiate plugins without wasmtime?</strong></summary>

The Web target implementation (`webMain` / `jsMain` / `wasmJsMain`) invokes `WebAssembly.Module` and `WebAssembly.Instance` directly through the browser's native WebAssembly runtime. A JavaScript runtime layer is embedded via Kotlin `js()` interop — no external JS files are emitted during compilation.

The runtime layer provides:

- **`wasi_snapshot_preview1` shims**: `fd_write` (UTF-8 stdout/stderr through `WasmlineLog` or `println`), `random_get` (`Random.nextBytes`), and `clock_time_get` (`Date.now()` converted from milliseconds to nanoseconds)
- **Wasmline bridge protocol** (`env` namespace): `bridge_inbound_copy_params`, `bridge_inbound_set_response`, `bridge_outbound_call_host`, `bridge_outbound_get_response`

`WasmlineWeb.prefetch(url)` downloads the raw `.wasm` bytes with Fetch. The suspending `WasmlineLoader.load(url)` call then resolves those cached bytes and instantiates the module. AOT-compiled artifacts (`.cwasm`, `.pwasm`) are not accepted by the browser path.

</details>

<details>
<summary><strong>What distinguishes <code>.cwasm</code> from <code>.pwasm</code> artifacts — and why not raw <code>.wasm</code>?</strong></summary>

These artifact types are related through Wasmline's pipeline, but they differ fundamentally in when compilation happens and what the compilation target is:

| Artifact | Compiled | Execution | Version coupling |
|---|---|---|---|
| `.wasm` | Source format; loaded directly by the browser path | Browser WebAssembly runtime | **None** — not coupled to Wasmtime |
| `.cwasm` | Ahead-of-time by `wasmtime compile` via Cranelift | Directly on native hardware (e.g., arm64 machine code) | Coupled to the wasmtime version that compiled it |
| `.pwasm` | Ahead-of-time by `wasmtime compile` targeting Pulley | wasmtime **Pulley** interpreter | Coupled to the wasmtime version that compiled it |

**`.cwasm` (platform-specific AOT)** produces native machine code for a particular target triple (e.g., `aarch64-android`). Maximum throughput; requires one artifact per platform.

**`.pwasm` (Pulley AOT)** is produced by `wasmtime compile` for the **Pulley** bytecode ISA instead of native machine code. The Pulley interpreter executes it at runtime. A `.pwasm` file is not raw WebAssembly: it is a precompiled, Wasmtime-version-coupled artifact. A `pulley64.pwasm` artifact runs across supported 64-bit native Wasmtime targets; 32-bit targets use a matching `pulley32.pwasm` artifact.

Raw `.wasm` is accepted directly only by the browser path. Wasmline's native runtime requires a precompiled `.cwasm` or `.pwasm`; both are outputs of a specific wasmtime release, so upgrading wasmtime invalidates them and requires recompilation.

Wasmline's native runtime does not load raw `.wasm` through the Pulley engine. Generate `.pwasm` ahead of time so the Pulley interpreter can execute the precompiled bytecode without an in-process compilation step; this is especially important in memory-constrained environments such as Android.

<Callout type="info" title="Version coupling">
  Both `.cwasm` and `.pwasm` are **version-coupled to the wasmtime compiler** that produced them. Upgrading the wasmtime version invalidates all previously compiled artifacts — they must be recompiled. This version coupling is why every non-Web native target uses pre-compiled `.cwasm` or `.pwasm` rather than raw `.wasm`. The Web target is the sole exception, relying on the browser's own WebAssembly runtime with raw `.wasm` files.
</Callout>

</details>

<details>
<summary><strong>Which engine module should load each artifact?</strong></summary>

| Engine module | Supported artifacts | Selection policy |
|---|---|---|
| `wasmline-engine-cranelift` | `.cwasm` and `.pwasm` | Prefer a matching `.cwasm`; fall back to portable `.pwasm` |
| `wasmline-engine-pulley` | `.pwasm` only | Execute portable bytecode through the Pulley interpreter |
| iOS runtime | `.pwasm` only | iOS uses the Pulley interpreter because native executable AOT is unavailable |

The engine module and artifact format are related but not interchangeable names. `.cwasm` contains platform-native Cranelift output, while `.pwasm` contains Pulley bytecode. The Cranelift Wasmtime build includes both runtime capabilities; the Pulley-only build includes only the Pulley side.

</details>

<details>
<summary><strong>How do Core Wasm, Raw Export, and Component Model calls differ?</strong></summary>

Use `WASMLINE_SERVICE` with either execution model for the same action-and-byte service API: Core uses the existing linear-memory bridge, while Component Model uses the fixed `wasmline.wit` envelope. Use `CORE_WASM` with `RAW_EXPORT` for an explicitly declared numeric export ABI. Use `COMPONENT_MODEL` with `COMPONENT_EXPORT` for business-specific typed WIT values.

The runtime path starts with a precompiled Component `.cwasm` or `.pwasm` artifact. Wasmline does not run `wit-bindgen`, `wasm-tools`, or `wasmtime compile` while loading it. The optional plugin build pipeline supports WIT binding generation, Component assembly, and Component AOT compilation through plugin-core, Gradle, and CLI; `contractMetadata` still describes the export contract and is not a WIT compiler input. See the [Wasmline Service guide](/en/docs/component-service).

</details>

<details>
<summary><strong>What happens when a plugin has no bound action?</strong></summary>

The call returns `WasmlineCallResult.Failure` with `WasmlineErrorCode.ACTION_NOT_BOUND`. It does not return an empty successful payload and does not crash the host. Unknown actions, invalid payloads, handler failures, traps, and malformed response frames follow the same result-first rule when the runtime can construct a reliable result.

Use `callResult`, `invokeRawResult`, or `invokeComponentResult` and inspect `Failure.failure.code`. `getOrNull()` and `failureOrNull()` are non-throwing helpers. `throwOnFailure()` is an explicit adapter for callers that choose exception-style handling; it is not the default transport behavior.

</details>

<details>
<summary><strong>What do <code>WLMF</code> and <code>frameVersion</code> mean?</strong></summary>

`WLMF` is a four-byte magic marker for the Wasmline Core response frame. It identifies the response format and is not a signature, encryption mechanism, or security check. Integrity and authenticity are handled by the artifact hash, manifest, and signature mechanisms.

`frameVersion` is a one-byte response layout version. The current value is `1`; it is not a Wasmtime version, Kotlin version, framework version, or business API version. Readers accept only the current value, `1`. Raw Export and Component Model calls do not use this Core response frame.

</details>

<details>
<summary><strong>Is the Kotlin IR compiler plugin mandatory for host integration?</strong></summary>

The compiler plugin is not mandatory. The low-level `Wasmline.call(action, bytes): ByteArray` API is always available for manual dispatch. Without the `wasmline-kotlin-plugin` applied — typically via the `wasmline-gradle-plugin` — `link<T>()` and `bind(impl)` call sites throw `UnsupportedOperationException` at runtime.

</details>

<details>
<summary><strong>What is the plugin execution isolation model?</strong></summary>

On native targets, each plugin invocation executes within a dedicated `Session` instance maintaining its own Wasm linear memory region. Plugins have no access to host process memory, the host filesystem, or the network unless the host explicitly provisions WASI capabilities through the wasmtime preopened-directory or socket-capability model. On Web targets, equivalent memory isolation is enforced by the browser's native WebAssembly sandbox.

</details>
